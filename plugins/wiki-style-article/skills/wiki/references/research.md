# 調べる工程

SKILL.md の工程 3〜5 の細目。本家の記事を読み、観点を組み直し、担当を並べて材料を書かせ、材料を確かめるまで。`wiki-with-rumor` のスキルも、この工程をそのまま使う（違うのは、噂・考察も集めることだけ）。

## 本家の記事の読み方

本家（ja.wikipedia.org）の記事は、同名の記事と関連の記事を合わせて 5 本まで読む。このスキルは公開の道具で、多くの人が使うと本家への負担になるので、この上限を超えない。本家の記事が無い題材もある。そのときは読まずに進む。

- 1 本につき 1 回だけ取る。見た目の HTML ではなく、ウィキテキストの生の文を取る。節の並び・本文・出典（`<ref>` の中）が一度に読め、本家の負担も小さい。
  `https://ja.wikipedia.org/w/index.php?title=<記事名>&action=raw`（記事名の空白は `_`。日本語はそのままか、URL エンコードする）
- 関連の記事は、同名の記事の「関連項目」と本文の内部リンク（`[[…]]`）から、題材にじかに関わるものを選ぶ。本家を検索して探さない
- ページを取る道具が無い（検索だけの道具）なら、検索の結果に出る本家の記事の抜き出しで足りる分だけ使い、取りに行かない

読んで取るもの:

1. 節の並び（`== 見出し ==` の並び）。類型のファイルの「節の並び」と比べ、この題材に特有の節（例: 「社会的影響」「アニメ」）を見つける
2. 論点。本家が触れている出来事・評価・論争のうち、記事に入れるべきもの
3. 元の資料の手がかり。`<ref>` の中の書名・記事名・発行元・日付・URL。保存版の URL（`archive-url=`、`web.archive.org`）があれば、元の URL と組にして拾う（元のページは消えていることが多く、保存版でしか読めないことがある）。観点ごとに分けて担当に渡し、担当が自分で元の資料を開いて確かめる

取らないもの:

- 本家の文。写さず、言い換えて流用もしない。記事の文は材料の出典から書く
- 本家そのものを出典にすること。ウィキペディアとその転載サイトは出典にならない（検査が `REF-WIKIPEDIA` で止める）
- 本家の `<ref>` の中身を、開かずに出典として書き写すこと。開けなかった資料は、下の「確かさ」で扱う

## ページの取り方

担当も書き手も、ページは次の順に取る。

1. `WebFetch` で取る
2. `WebFetch` で取れないとき（web.archive.org の保存版は WebFetch が断る）、スキルのフォルダの取得のコマンドで取る
   `sh <スキルのフォルダ>/scripts/wiki.sh fetch <URL>`
   保存版は飾りの無い形に直して取り、同じホストへは間を空ける（web.archive.org は 15 秒。並んだ担当とも順番を分け合う）。長い本文は `--max-chars` で区切られるので、続きは出力の最後に出る `--offset` を付けて流し直す。HTML だけを扱う
3. それでも取れないとき（JS で描くページ、403、PDF）、`WebFetch` で `https://r.jina.ai/<URL>` を取る（鍵なしの Jina の Reader。毎分 20 回まで）。Jina は鍵なしでは web.archive.org を止めているので、保存版には使わない
4. どれでも取れなければ、取れなかったことを材料に書く（下の「確かさ」）

archive.ph（archive.today）は CAPTCHA が出て、どの手段でも取れない。本家が archive.ph を引いていたら、元の URL か web.archive.org の保存版を探す。

## 観点の組み直し

類型のファイルの「調べる観点の下敷き」を元に、読んだ記事を見て観点を決める。

- 大きい観点は分ける。例: 漫画の題材で、アニメの展開が本家で大きな節を持つなら、「メディア展開」を「アニメ」と「その他の展開」に分ける
- 薄い観点は合わせる。例: 書誌の情報が少ないなら、「書誌情報」を「制作の経緯」に合わせる
- 観点は 8 つまで。超えたら近いものを合わせる
- 観点ごとに、担当に渡す短い英字の名前（`history`・`anime` など、英小文字とハイフン）を決める。材料のファイル名と出典のキーの頭に使う

## 担当への頼み方

観点ごとに担当を 1 人ずつ起こし、全員を一つのメッセージで並べて走らせる。担当は前面で走らせ、裏に回さない。全員がそろうまで同じターンの中で待ってから、工程 5 に進む。

裏に回すと、担当の終わりが後のターンに届く。SKILL.md の `allowed-tools` が効くのはスキルを呼んだターンの中だけなので、ターンをまたいだ担当はページの取得や書き込みを拒まれる（試しで、裏に回した担当の一部が書き込みを拒まれ、前面では 3 回とも通った）。

- Claude Code: このスキルのプラグインに同梱した担当 `researcher` があればそれを使う。無ければ汎用の担当を、モデル `sonnet` で起こす
- Codex など: 担当を並べて起こせるなら、観点ごとに並べ、全員を待つ。起こせないなら、一人で観点を順に調べ、同じ形で材料を書く

担当への指示は、次の雛形の `<…>` を埋めて渡す。担当は会話の履歴を見られないので、題材と範囲をここに書き切る。

作業フォルダとスキルのフォルダの絶対パスは、道具が渡す情報（今いるフォルダ、スキルを読み込んだときのフォルダ）から組む。パスを調べるためだけにシェルのコマンドを流さない（利用者に余計な確認が出る）。

```text
日本語版 Wikipedia 風の記事を書くための材料を集める。あなたは観点「<観点の名前>」の担当。

題材: <記事名>（<一行の説明>）
扱う範囲: <範囲。入らない話題があれば書く>
この観点で集めること: <この観点の節に書く中身。例: 連載が決まった経緯、作者が語った着想、連載の開始と終了>
手がかり: <本家の記事から拾った元の資料の題・発行元・日付・URL。保存版があれば「元の URL ／ 保存版の URL」の組で書く。無ければ「無し」>
噂・考察: <集めない。/ 集める（wiki-with-rumor のとき）>

材料は <作業フォルダの絶対パス>/材料/<観点の英字の名前>.md に書く。形は次の「材料の形」に従う。
出典のキーは「<観点の英字の名前>-」で始める（例 history-news-start）。

ページの取り方: まず WebFetch。取れなければ（web.archive.org など）
  sh <スキルのフォルダの絶対パス>/scripts/wiki.sh fetch <URL>
を流す（cd や && でつながない）。PDF・403・JS で描くページは WebFetch で https://r.jina.ai/<URL> を取る（web.archive.org には使わない）。
元の URL が 404・403・題しか取れないときは、手がかりの保存版の URL を wiki.sh fetch で取る。手がかりに保存版が無ければ、https://web.archive.org/web/2020/<元の URL> のように年を入れた保存版の URL を作って wiki.sh fetch で試す（保存版が無ければ 404 が返る）。
「取れなかった」「見つからなかった」と書くのは、この順を試したあとだけ。何を試したか（WebFetch・fetch・保存版・Jina）を材料に書く。

止めどき: 節を書くのに足りる事実が出典つきで集まったら止める。目安は出典 3〜8 件。ページを開くのは 15 回まで。

出典の選び方と、事実の「確かさ」:
- 公式・当事者の発表（一次資料）と、新聞・雑誌の記事・書籍・批評（二次資料）の両方を探す。
  評価・解釈・影響・因果は、二次資料に書かれているものだけを「確か」にする
- 日本語の資料を、同じ程度の資料なら外国語より先に使う
- 確か: 信頼できる資料（上の一次・二次資料）を開いて確かめた事実
- 弱い出典だけ: 攻略 Wiki・個人のブログ・SNS・掲示板・まとめサイトにしか無い事実。その出どころを出典に書き、weak = true を付ける
  （本人についての事実を本人の公式の発信が出した場合は、弱い出典にしない）
- 元を特定できない: 検索の要約や他のページの言及で見かけたが、元のページを開けない・特定できない事実。出典を付けず、どこで見かけたかを書く
- Wikipedia とその転載サイトは、どの確かさでも出典にしない
- URL は自分で開いて中身を確かめたものだけを出典に書く。題や URL を推測で作らない
- 数値・日付・固有名詞は、出典の表記のとおりに写す
- 出典どうしが食い違えば、両方を残し「食い違い」に書く
- 何も見つからなかったことだけを「見つからなかったこと」に書く。「無い」とは書かない

噂・考察を集めるとき（「集める」のときだけ）:
- 事実として確かめられていない、人の見方・推測・非難も集め、事実の項目に「種類: 噂・考察」と書く
- 誰の見方か（SNS の利用者、まとめサイト、掲示板の書き込み、評論家の誰それ）を書く
- 特定の人や会社への非難のような強い主張は、互いに写しでない出どころ（掲示板と、それを転載したまとめは一つと数える）をいくつ見つけたかを書く

終わったら、書いたファイルのパスと、集めた事実の件数（確かさ・種類ごと）・出典の件数・見つからなかったことを短く報告する。
```

## 材料の形

担当は `材料/<観点の英字の名前>.md` に、次の形で書く。出典は原稿の `[refs.<キー>]` と同じ項目で書くので、書き手はそのまま原稿に写せる（項目の意味は `source-format.md` の「出典」）。

````markdown
# 材料: 制作の経緯（星屑ラーメン）

## 出典

```toml
[refs.history-news-start]
kind = "news"
title = "新連載「星屑ラーメン」始まる"
work = "架空新聞"
date = "2020-04-01"

[refs.history-official]
kind = "web"
title = "作者インタビュー"
url = "https://example.com/hoshikuzu/interview"
publisher = "架空出版"
access_date = "2026-11-02"

[refs.history-fanwiki]
kind = "web"
title = "星屑ラーメン 攻略wiki 制作秘話"
url = "https://example.com/wiki/hoshikuzu"
publisher = "有志の攻略wiki"
access_date = "2026-11-02"
weak = true
```

## 事実

1. 連載は2020年4月に始まった。[^history-news-start]
   > 確かさ: 確か
   > 引用: 「4月号から新連載が始まる」
2. 作者は、屋台を舞台にした理由を、学生時代に通った屋台の記憶だと述べている。[^history-official]
   > 確かさ: 確か
   > 引用: 「学生のころ毎晩のように通った屋台が原点です」
3. 連載の前に、読み切りの試作が一度描かれた。[^history-fanwiki]
   > 確かさ: 弱い出典だけ（攻略 Wiki）
   > 引用: 「連載前に読み切り版があった」
4. 屋台の名前は、作者の地元の店から取られた。
   > 確かさ: 元を特定できない（検索の要約で見かけたが、元のページを特定できなかった）

## 食い違い

- 連載の開始: history-news-start は 2020年4月号、history-xxx は 2020年5月号と書く

## 見つからなかったこと

- 単行本の累計部数（公式サイト・出版社の発表・報道を探して、何も見つからなかった）
````

- 事実は 1 件 1 項目。文は常体で、出典に書かれた範囲を超えない。複数の出典で支えるなら印を並べる（`[^a][^b]`）
- 「確かさ」は「確か」「弱い出典だけ」「元を特定できない」のどれか。噂・考察を集めるときは、項目に「種類: 噂・考察」の行を足す
- 引用は、事実を支える出典の中の文を短く（1〜2 文）写す。書籍で文を写せないときは「p.23 に記述」のように書く
- 閲覧日 `access_date` は、ページを開いた日（`YYYY-MM-DD`）
- 中身の無い見出し（食い違いが無いなど）は、見出しの下に「無し」と書く

## 材料を確かめる

工程 5 で、書き手は材料を全部読んでから原稿を書く。

- 引用が事実を支えているかを見る。支えていない事実は、確かさを一段下げて扱う（引用の無い「確か」は「元を特定できない」として扱う）
- 同じ資料が別の担当から別のキーで出たら、一つのキーにまとめ、本文の印もそろえる
- 「食い違い」は本文で両方を書く。どちらかに寄せない
- 確かさに応じて印を付けて原稿に書く（`source-format.md` の「印と警告の枠」）。確かめられなかった事実を落とさない
- 「見つからなかったこと」だけは記事に書けない。渡すときに、何も見つからなかった観点として伝える
- 足りない観点があれば、その観点だけ担当を起こし直す。起こし直すのは一度まで
