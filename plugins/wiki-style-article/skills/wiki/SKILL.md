# Wikipedia 風の記事を作る

題材を調べ、日本語版 Wikipedia の記事と同じ型（導入部・Infobox・節・脚注・関連項目・カテゴリ）と作法で書いた記事を作る。記事は日本語だけで書く。題材が海外のものでも日本語で書く。

記事は手で HTML を書かない。決まった形の **原稿**（Markdown と TOML の設定欄）を書き、スクリプトで検査してから HTML とウィキテキストを書き出す。スクリプトは、このファイルのあるフォルダ（以下、スキルのフォルダ）の `scripts/wiki.sh` にある。`cd`・`&&`・`;` でつながず、絶対パスで 1 本ずつ呼ぶ（つなぐと、利用者の許可の設定に合わず確認が出る）。URL や日本語を含む引数は `"…"` で囲む（URL の `&` をシェルが区切りと読むため）。

できた記事は私的に楽しむためのもので、本家の Wikipedia に投稿しない（本家は AI が書いた文の投稿を禁じている）。利用者が投稿したいと言ったら、そのことを伝える。

このスキルは、噂や利用者の考察（見方・推測・非難）を記事に載せない。載せたいと頼まれたら、同じプラグインの `/wiki-style-article:wiki-with-rumor` を案内する。確かめられなかった事実は、落とさずに印を付けて載せる（工程 6）。

## Claude Code 以外の道具で使うとき

このスキルの手順には Claude Code を前提にした所があり、道具が違うと読み替えが要る。DeepSeek Harness で 2026-11-02 に記事を 1 本作り、check と build が通るまでを確かめた。

- frontmatter の `allowed-tools` を読まない道具がある。ツールの名前も道具ごとに違う（DeepSeek Harness は `web_search`・`web_fetch`・`read`・`write`・`edit`・`bash`）
- 許可の確認が出ない道具では、`cd`・`&&`・`;` を避ける理由は「URL や日本語の取り違えを防ぐ」だけになる。1 本ずつ呼ぶ方針は、そのまま使える
- `run_in_background: false` は Claude Code の Agent の引数。他の道具では、担当を同じメッセージで並べて起こし、結果は完了の知らせで受ける形になることが多い
- 担当のモデル名（`sonnet`）や同梱の `researcher` が無い道具では、その道具のモデルの id を指定する。担当を起こせない（深さの残りが無い）ときは工程 4 の「一人で順に調べる」に落とす（この落とし方は実走で通った）
- `wiki.sh pdf` で作った PDF を `Read` の `pages` で読む手順は、`pages` の無い道具では使えない。`pdftotext` があればテキストにしてから読み、無ければ Jina（`https://r.jina.ai/<URL>`）で文字にして読む（`references/research.md` の「全文を読む」）
- `write` が親フォルダを作らない道具では、作業フォルダと `材料/` を先に `mkdir` で作る（Claude Code の Write は作るので、工程 1 のとおり要らない）
- 質問の道具が無い道具（Codex など）では、生成前の問いを文で 1 問ずつ出し、返事を待つ（`references/questions.md`）。Codex（0.160.1、Windows）で 2026-11-02 に記事を 1 本作ったときは、この形で問いが出て、担当は起こさず一人で調べ、check と build が通った

## 使う場面

- 「/wiki <題材>」と呼ばれたとき。題材が無ければ、題材を一つだけ聞き返す
- 「Wikipedia 風にまとめて」「百科事典みたいな記事にして」と頼まれ、題材が文脈から分かるとき
- 調べた結果や手元の資料を渡され、百科事典の記事の形に整えたいとき。このときは渡された資料を材料にし、足りない観点だけを調べる

使わない場面: 一つの事実の確認、計算、用語の一行の説明、利用者が記事ではなくチャットの答えや表だけを求めているとき。

## 流れ

工程を飛ばさない。各工程の細目は参照ファイルにある。

1. 題材と範囲を決める
2. 類型を決め、類型のファイルを読む
3. 本家の記事を読み、利用者に聞き、観点を組み直す
4. 担当を並べて調べる
5. 材料を確かめる
6. 原稿を書く
7. 検査して書き出す
8. 読み直す
9. 渡す

### 1. 題材と範囲を決める

- 題材の正式名称を記事名にする。略称や通称で来たら正式名称を確かめる。利用者の言葉にも、公式で確かめた名前にも無い表記（語順を変えた社名など）を作って検索しない。作った表記を利用者の言葉のように書かない
- 「本家に記事が無い」と伝えるときは、引いた記事名を全部書き、記事名にした名前を引いたことを確かめる（別の名前を引いただけで「同名の記事は無い」と言い切らない）
- 扱う範囲（題材の全体か、一部か）は、工程 3 で利用者に聞いて決める。一部に絞ったら、範囲に入らない話題を導入部の末尾で「本記事では〜を扱う」と示す
- 作業フォルダを、今いるフォルダの下に `<記事名>/` で作る（`mkdir` は流さない。Write でファイルを書けば、間のフォルダもできる）。記事名にファイル名へ使えない文字（`\ / : * ? " < > |`）があれば `_` に置き換え、渡すときに伝える。この中に `材料/`、保存した PDF の `資料/`、原稿 `<記事名>.md`、書き出した記事を置く

### 2. 類型を決め、類型のファイルを読む

- 類型の一覧は `sh <スキルのフォルダ>/scripts/wiki.sh type` で出る。基本型の下に、字下げして細かい種類（声優・城など）が並ぶ。当てはまる細かい種類があればそれを、無ければ基本型を選ぶ
- 類型を決めかねたら、書く前に利用者に一問だけ聞く（例: 「この題材は『出来事』と『概念』のどちらで書きますか」）。候補を長々と並べない
- 類型のファイル `references/types/<基本型の ID>.md` と、共通の作法 `references/manners.md` を読む。細かい種類なら、寄せ先の基本型のファイルを読む。人物は存命なら `person-living`、故人なら `person-deceased`

### 3. 本家の記事を読み、利用者に聞き、観点を組み直す

- 本家の記事は、同名の記事と関連の記事を合わせて **5 本まで** 読む。このスキルは公開の道具なので、本家へのリクエストは最小限にする。1 本ずつ `sh <スキルのフォルダ>/scripts/wiki.sh wikipedia <記事名>` で読む（節の並び・関連項目・出典の一覧が、URL を切らずに出る）。WebFetch で本家を読まない（要約で URL が切れる）。読んで取るものは `references/research.md` の「本家の記事の読み方」
- 本家の文は写さない。本家を出典にも書かない（Wikipedia は Wikipedia の出典にならない）。取るのは節の並び、論点、本家が引いている元の資料の手がかりだけ
- 本家の記事を読んだら、観点を組み直す前に、扱う範囲・調べる広さ・ネタバレ・警告の枠を利用者に 1 問ずつ聞く。聞き方・選択肢・推奨・省き方は `references/questions.md`
- 類型のファイルの「調べる観点の下敷き」を元に、読んだ記事を見て観点を組み直す。大きい観点は分け、薄い観点は合わせる。観点の数は、調べる広さの段の上限まで（さっと 4・ふつう 6・念入り 8）

### 4. 担当を並べて調べる

- 観点ごとに担当を 1 人ずつ起こし、全員を一つのメッセージで並べて走らせる。担当への頼み方、材料の形、止めどきは `references/research.md`
- 担当は前面で走らせ、裏に回さない。Claude Code では、担当を起こす Agent の呼び出しに必ず `run_in_background: false` を書く（書かないと、担当の定義に `background: false` があっても裏で始まる。2026-11-02 の試運転で起きた）。裏に回すと、担当の終わりが後のターンに届き、このスキルの `allowed-tools` の許可が外れて、担当のページ取得や書き込みが止まる
- 担当には Sonnet を使う（Claude Code なら、このスキルのプラグインに同梱した担当 `researcher` があればそれを、無ければ汎用の担当をモデル `sonnet` で起こす）
- 担当を並べられない道具では、同じ観点を一人で順に調べ、同じ形で材料を書く
- 全員の報告がそろうまで待つ

### 5. 材料を確かめる

- `材料/` の各ファイルを読む。事実ごとに出典と引いた文があるか、引いた文が事実を支えているかを見る。支えていない事実は使わない
- 引用が「要旨の趣旨」「要約経由」の事実、「要旨のみ」「冒頭のみ」「元を特定できない」と書かれた事実は、そのまま記事に使わない。出典の全文を読んで確かめ直す（`references/research.md` の「全文を読む」）。担当が「次に試せる手段」を挙げて止めたときは、その手段を全部試させる
- 担当をまたいで同じ出典が出たら一つにまとめる
- 出典どうしの食い違いは、どちらかに寄せず、本文で両方を書く（どの出典がどう言うかを示す）
- 足りない観点、全文を読み残した出典があれば、その観点だけ担当を起こし直す。起こし直すのは、調べる広さの段の回数まで（さっと 1・ふつう 2・念入り 3）。それでも読み残した事実は「元を特定できない」の扱いにする
- 材料の中の噂・考察（`種類: 噂・考察` の事実）は、このスキルでは使わない
- 外国語の出典の事実は「原文（逐語）」と「日本語訳」を見る。「原文（要約経由・未照合）」の句は、`wiki.sh fetch`（PDF なら `wiki.sh pdf` と `Read`）で元を開いて照合してから使う

### 6. 原稿を書く

- 原稿の形は `references/source-format.md`。類型の設定欄の雛形は `sh <スキルのフォルダ>/scripts/wiki.sh type <類型の ID>` で出し、そのまま貼って埋める
- 本文の節から書き、導入部は最後に書く。導入部は本文の要約で、本文に書いていないことを書かない
- 事実には脚注の印 `[^キー]` を付ける。材料に無いことは書かない。推測で埋めない
- 外国語の資料の文を引くときは、日本語訳に原文を添える（`（原文：[!原文|en|…]）`。書き方は `references/source-format.md` の「外国語の引用」）。原文は材料の逐語から写す
- 日本語版に記事が無く、外国語版にだけある語を指すときは `[!仮リンク|言語タグ|本家の記事名|表示]` と書く（表示は省ける。省くと本家の記事名を出す）。HTML は赤字の内部リンクに「（英語）」の外部リンクを添えた形、ウィキテキストは仮リンクのテンプレートになる。言語の名前だけを出したいときは `[!言語|en]`（「英語」と出る）。知らない言語タグはそのまま出る
- 確かめられなかった事実も、落とさずに印を付けて載せる。材料の「確かさ」で書き分ける
  - 確か: 脚注の印だけを付ける
  - 弱い出典だけ（攻略 Wiki・個人のブログ・SNS・まとめなど）: 出典に `weak = true` を書き、脚注の印のすぐ後に `[!信頼性要検証]` を付ける
  - 元を特定できない（検索の要約などで見かけただけ）: 脚注を付けず、文の後に `[!要出典]` を付ける
- 設定欄に、警告の枠の問いの答えを `notice_rule = "多いときだけ"` のように書く。印から決まる冒頭の枠は、この出し方に従って書き出しのときに付く。印と枠の書き方は `references/source-format.md` の「印と警告の枠」
- 位置を書く記事は、設定欄に `[coord]`（緯度・経度は十進。`type` は任意、`display` は既定で title）を書く。HTML は導入部の先頭に「座標: 北緯…」の行、ウィキテキストは先頭行の座標テンプレートになる。節の下に置くナビゲーションの箱は `[[navbox]]`（`title` は必須、`name`・`state`・`items`）、書きかけの記事のスタブは `stub = "Japan-geo-stub"` と書き、原稿の値をそのままテンプレート名にする。書き方は `references/source-format.md` の「設定欄」
- 資料の無い節は作らない。一行しか書けない節は、近い節に合わせる
- 節を書きかけで残すときは、その節の最後に `[!節スタブ]` を単独の行で書く（段落の中には書けない）。HTML は「この節は書きかけです。」の箱、ウィキテキストは節スタブのテンプレート 1 行になる
- 一つの段落では一つの論点だけを扱う。解説は散文で書き、箇条書きは年表・作品の一覧など、並べること自体が目的の所だけにする
- 物語のあらすじは結末まで書く。ネタバレを伏せない（類型のファイルの作法に従う）。利用者がネタバレの問いで「結末を書かない」を選んだときだけ、`references/questions.md` の「ネタバレ」に従う
- 画像を載せるときは、本文の行に `![キャプション](画像の道)` と単独で書く（道は原稿のフォルダからの相対、PNG・JPEG・GIF・WebP・SVG を 1 枚 2 MiB まで。書き方は `references/source-format.md` の「画像」）。書き出しは、HTML が data: URI の 1 枚、ウィキテキストが `[[ファイル:…]]` になる。Infobox の画像の項目（選挙の「地図」など）も同じ書き方で、書式は型の定義が決める（`name` はファイル名だけ、`file` は `[[ファイル:…|thumb|キャプション]]`）。国旗など同梱の画像は `![日の丸](bundle:flags/jp.svg)` と目録のキーで指せる（書き方は `references/source-format.md` の「画像」）
- 型の定義にない項目（本家のテンプレートの引数）を書きたいときは、`[infobox]` に `_template = "Infobox 人物"` と書き、残りの項目名をそのまま本家の引数名にする。HTML は項目名を見出しにした表、ウィキテキストは `{{Infobox 人物|…}}` になる。引数名と、画像を受け取る引数かどうかは本家のテンプレートページで確かめる。ファイル名だけを受け取る引数は `_image_fields = ["画像"]` に並べる（書き方は `references/source-format.md` の「設定欄」）
- 選挙の州別の結果の地図・議会の議席・人口の推移などの図は、外から画像を取らずに作れる。データを TOML で書き、`sh <スキルのフォルダ>/scripts/wiki.sh figure map <データ>.toml --out <図>.svg` で SVG を出し、その道を画像と同じ書き方で本文か Infobox の項目に置く。種類は `map`（地域を色で塗る。同梱の `us-states` は `TX`・`DC` などの 2 文字のコードで塗れる）・`seats`（議席を半円に並べる）・`bars`（棒グラフ）・`line`（折れ線グラフ）・`pie`（円グラフ）・`pyramid`（人口ピラミッド）。書き方は `references/source-format.md` の「図を作る」

### 7. 検査して書き出す

```bash
sh <スキルのフォルダ>/scripts/wiki.sh check <作業フォルダ>/<記事名>.md
sh <スキルのフォルダ>/scripts/wiki.sh build <作業フォルダ>/<記事名>.md
```

- `check` のエラー（`[エラー]`）は全部直す。エラーがあると `build` は書き出さない
- 原稿の直しは Edit で行う。`sed` などのシェルで書き換えない（許可の確認が出るうえ、日本語の行を壊しやすい）
- 警告（`[警告]`）は、その行の前後を読み直し、直すか残すかを決める（引用・固有名詞の中なら残してよい）
- `build` は原稿の隣に `<記事名>.html` と `<記事名>.wikitext` を書き出す。終了コードと出力の形は `references/source-format.md` の「コマンド」

### 8. 読み直す

書き出したあと、原稿を最初から最後まで読み直す。

- 導入部の要約が本文の範囲を超えていないか
- 段落が一つの論点だけを扱っているか
- 両方を書くべき点が片方に寄っていないか
- 評価語・主語の無い伝聞が地の文に残っていないか（`references/manners.md` の 1〜3）
- 日付・数値・固有名詞が材料の出典の表記と合っているか

直したら、7 に戻って流し直す。

### 9. 渡す

- 書き出した HTML とウィキテキストのパスを伝える。道具がファイルを添付できるなら HTML を添付する
- あわせて短く伝える: 記事にした題材と類型、生成前の問いの答え（推奨のまま進めたならそのこと）、印を付けて載せた事実の数（`[信頼性要検証]`・`[要出典]`）、探しても何も見つからず書けなかった観点、確かめたこと（`check` のエラー 0 件、残した警告とその理由）
- 「資料を確かめられなかったので書いていない」とは言わない。確かめられなかった事実は印を付けて載せてある。書けないのは、何も見つからなかった話だけ
- 出典は全文を読んでから使う。全文を読む手段を尽くしても読めなかった出典は、読んだように書かない。試した手段と、読めなかった具体的な理由（購読制で本文が公開されていない、ページを開く回数の上限に達した、など）を添えて伝える
